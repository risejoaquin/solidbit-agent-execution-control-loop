# ADR-014: V1 Transport Authentication Model and Deferral of Package Signing

- **Status:** ACCEPTED
- **Date:** 2026-10-07
- **Scope:** SACL V1 Transport Security & Cryptographic Boundary
- **Deciders:** Joaquín (Sovereign Principal), SACL Security & Architecture Leads

---

## 1. Context

In early Wave 0 design drafts (`AG-ARCH` ADR-012, `AG-SEC` Section 2.4), a requirement was proposed mandating that all incoming execution packages must be cryptographically signed using an HMAC-SHA256 signature generated in the Cloud Control Plane (ChatGPT Web) and verified by the local Mail Gateway before execution.

However, subsequent operational and security analysis documented in the constitutional remediation baseline revealed critical vulnerabilities and practical impossibilities with this approach:
1. **ChatGPT Web Cannot Possess Private Secrets:** ChatGPT Web is an interactive conversational LLM interface accessed via a web browser. It does not possess a secure hardware security module (HSM), key management service (KMS), or isolated cryptographic enclave.
2. **Secret Leakage Risk:** Asking a conversational LLM to possess, manage, or calculate HMAC digests using a long-lived shared secret exposes that secret to conversation transcripts, LLM prompt histories, browser caches, and potential prompt exfiltration attacks.
3. **False Sense of Security:** An HMAC signature generated by an unauthenticated browser chat session does not provide genuine cryptographic non-repudiation or provenance; it merely creates security theater while introducing significant secret management liability.
4. **Absence of Real Key Custody:** True cryptographic signing requires a dedicated, isolated key custody component (such as a local signing CLI, HSM, or dedicated cloud KMS signer) that is not part of the V1 architecture.

Constitutional remediation established explicit corrections:
- **ChatGPT Web MUST NOT possess a long-lived HMAC or private signing secret.**
- **HMAC package signing is NOT a V1 requirement until a real signer/key-custody component exists.**
- V1 authentication relies on Gmail API `users.watch` and Google Cloud Pub/Sub pull authentication, Gmail API OAuth2 channel identity over TLS, strict protocol and schema validation, attachment SHA-256 integrity, replay/idempotency controls (`historyId`, `message_id`, `nonce`), local policy, and human approval for gated actions.
- Package signing remains deferred to future hardening waves.

---

## 2. Decision

We decide to **formally defer cryptographic package signing** and establish a pragmatic, multi-layered **Defense-in-Depth Authentication Model for SACL V1**:

1. **Explicit Deferral of Package Signing:**
   - Cryptographic package signing (HMAC-SHA256 or asymmetric digital signatures) is **formally deferred** to future hardening waves.
   - Package signing will only be introduced when an isolated, trusted key custody infrastructure (e.g. hardware token, KMS signer, or dedicated signing agent) is physically implemented outside the conversational web UI.
   - **ChatGPT Web MUST NOT possess, store, or be configured with any long-lived HMAC or private signing secret.**

2. **SACL V1 Multi-Layer Defense-in-Depth Authentication Model:**
   In lieu of package signing, SACL V1 secures inbound transport and execution through seven layered controls:

   ```
   +-----------------------------------------------------------------------------------+
   |                    SACL V1 DEFENSE-IN-DEPTH AUTHENTICATION LAYERS                 |
   +-----------------------------------------------------------------------------------+
   | 1. Transport Channel Auth  | Gmail OAuth2 / users.watch / Pub/Sub Pull over TLS |
   | 2. Zero-Webhook Ingress    | Outbound-only TLS connections; zero listening ports   |
   | 3. Sender Whitelisting     | Mail Gateway drops all senders != uniquedraken@...    |
   | 4. Subject Routing Hints   | Filters [SACL][JOB][v1][<JOB_ID>] without authority   |
   | 5. SHA-256 Integrity       | Attachment hashed upon receipt, logged to sacl_ops.db |
   | 6. Anti-Replay Controls    | (message_id, nonce) & (job_id, hash) & historyId sync |
   | 7. Hermetic Schema Check   | Strict manifest.schema.json & fail-closed Zip-Slip    |
   | 8. Machine Governance Gate | Prepend guard headers; Human Authority Gate for merge |
   +-----------------------------------------------------------------------------------+
   ```

   - **Layer 1: Transport Channel Identity:**
     - Relies on authenticated Google account credentials (OAuth2 refresh tokens) and Google Cloud service credentials stored securely in Windows Credential Manager or DPAPI. All transport occurs over encrypted TLS sessions.
   - **Layer 2: Zero-Webhook Ingress:**
     - The host workstation initiates all connections outbound (Google Cloud Pub/Sub StreamingPull and Gmail API HTTPS). No public webhook URL or inbound listening socket is ever exposed, eliminating unauthorized external network access.
   - **Layer 3: Strict Sender Whitelisting:**
     - The Mail Gateway inspects the message metadata retrieved via Gmail API. Messages from any address other than the explicitly whitelisted address (`uniquedraken@gmail.com`) are dropped or quarantined immediately without processing. Self-mail is supported.
   - **Layer 4: Subject Routing Hints:**
     - The email subject is matched against `^[SACL][JOB][v1][<JOB_ID>]`. The subject serves strictly as an intake routing hint and never confers execution authority.
   - **Layer 5: Attachment SHA-256 Integrity:**
     - The Mail Gateway computes the SHA-256 cryptographic digest of the received ZIP attachment immediately upon download. This hash is permanently recorded in `sacl_ops.db` and binds the physical package to all downstream execution attempts.
   - **Layer 6: Replay & Idempotency Controls:**
     - Anti-replay nonces, Gmail `message_id`, and `historyId` cursor states are tracked in SQLite (`mail_messages`, `mail_cursors`). Duplicate deliveries are ignored; conflicting resubmissions are rejected fail-closed.
   - **Layer 7: Hermetic Schema & Path Sanitization:**
     - The package is validated against `manifest.schema.json`, and all entries are checked for Zip Slip vulnerabilities prior to extraction.
   - **Layer 8: Machine Governance & Human Authority Gates:**
     - All execution occurs in isolated git worktrees with dynamic prompt guard injection (`MERGE=NOT_AUTHORIZED`, `DEPLOY=NOT_AUTHORIZED`). Irreversible actions require physical human sign-off via the Human Authority Gate.

## 3. Consequences

### Positive
- **Elimination of Secret Leakage:** Zero risk of long-lived cryptographic secrets leaking via LLM chat logs, browser caches, or prompt exfiltration.
- **Realistic V1 Operationalization:** Removes an impossible operational requirement from the ChatGPT Web workflow, allowing frictionless authoring of wave packages.
- **Robust Defense-in-Depth:** Multiple redundant security controls (TLS transport, sender whitelist, payload hashing, anti-replay, schema validation, worktree isolation, human gates) provide strong, realistic security without relying on brittle chat-based HMAC.
- **Clear Future Upgrade Path:** Establishes explicit prerequisites for introducing cryptographic package signing in later implementation waves when real key custody becomes available.

### Negative / Trade-Offs
- **Absence of Cryptographic Non-Repudiation:** Package integrity relies on the security of the Gmail transport channel, Google Cloud authentication, and local hashing rather than an end-to-end digital signature from author to executor.
